# Решения

## db (`src/db/schema.ts`)

### Только Postgres (`drizzle-orm/pg-core`)

- Что: схема и запросы пишутся только под Postgres.
- Почему: в Drizzle нет общих для всех диалектов типов колонок и `Db`. `onConflictDoUpdate` и `returning` есть не везде: в MySQL их нет.
- Отклонено:
  - интерфейс `Storage` в ядре и отдельные реализации под каждую базу;
  - фабрики схемы под каждый диалект с объединением типов `Db`.

### Схема по умолчанию — `arcwave`, таблицы `users` / `accounts` / `sessions`

- Что: таблицы создаются в Postgres-схеме `arcwave`, без префикса в именах. `schema: "public"` создаёт их через `pgTable`, без явной схемы.
- Почему: таблицы библиотеки не смешиваются с таблицами приложения, поэтому префикс не нужен. `pgSchema("public")` в Drizzle бросает ошибку.
- Отклонено:
  - `public` по умолчанию;
  - префикс `arcwave_` (`arcwave.arcwave_users`);
  - другие имена по умолчанию для `public`: это скрытая логика. Вместо этого README советует передать `tableName`.

### Точка входа `arcwave/schema` с готовыми таблицами

- Что: `src/db/schema.ts` публикуется как `arcwave/schema`. Помимо функций `create*Table`, он экспортирует готовые `arcwaveSchema`, `users`, `accounts` и `sessions`. Пользователь реэкспортирует их одной строкой из своего файла схемы:

  ```ts
  export { arcwaveSchema, users, accounts, sessions } from "arcwave/schema";
  ```

- Функции `create*Table` остаются и в `arcwave/h11`, для совместимости.
- Для своего имени схемы пользователь сам экспортирует `pgSchema("<имя>")` и вызывает `create*Table({ schema })`.
- Почему:
  - `drizzle-kit` загружает файл схемы через `require()` и берёт только экспортированные `PgTable` и `PgSchema`, имя экспорта не важно;
  - `CREATE SCHEMA` генерируется только для экспортированного `PgSchema`;
  - готовый экспорт избавляет пользователя от ручного `pgSchema("arcwave")` и трёх вызовов `create*Table`.
- Проверено на собранном пакете (`bun pm pack`) в Node 24: `generate` создаёт схему, таблицы, внешние ключи и индексы, `push` применяет изменения.
- Отклонено:
  - только ручной `pgSchema(...)` в файле пользователя без готовых таблиц;
  - `CREATE SCHEMA IF NOT EXISTS` при запуске приложения: миграции идут раньше запуска, и библиотеке понадобились бы права на изменение структуры базы;
  - передача объекта `PgSchema` в опции вместо строки: это меняет API;
  - экспорт из основной точки входа `arcwave`:
    - общие имена `users`, `accounts`, `sessions` попадают в корень пакета;
    - `drizzle-kit` при чтении схемы тянет весь пакет, вместе с провайдерами и `jose`.

### `schemaFilter` — на стороне пользователя

- Что: README просит добавить `schemaFilter: ["public", "arcwave"]` в `drizzle.config.ts`.
- Почему:
  - `push` и `pull` по умолчанию смотрят только схему `public` и молча пропускают таблицы arcwave;
  - для `generate` и `migrate` эта настройка не нужна;
  - конфиг принадлежит пользователю, библиотека не может задать его сама.

### Время — `timestamp with time zone`

- Что: все колонки времени объявлены как `timestamp(..., { withTimezone: true })`.
- Почему:
  - `timestamp` без пояса понимают по-разному: Drizzle пишет и читает `Date` как UTC, а `DEFAULT now()` Postgres пишет в поясе сессии базы;
  - если сессия базы не в UTC, `created_at` и `updated_at` сдвигаются, а сравнения с `now()` в SQL ломаются. Проверено на PGlite с `Europe/Moscow`: сдвиг +3 часа;
  - `timestamptz` занимает те же 8 байт, а Drizzle возвращает тот же `Date`.
- Отклонено: `timestamp` без часового пояса.

## providers (`src/providers/`)

### Яндекс: почта из `default_email`

- Что: `YandexAuth.getUser` берёт `default_email` и считает его подтверждённым. Если поля нет — ошибка `Invalid email`.
- Почему: у Яндекс ID нет аналога `email_verified`. `default_email` — это почтовый ящик самого аккаунта, и по документации массив `emails` сейчас не содержит ничего другого. Допущение записано комментарием в коде, как у GitHub.
- Отклонено: не выпускать провайдер, пока проверить нельзя.

### Яндекс: имя из `display_name`

- Что: `Account.name` — это `display_name`, без него ошибка `Invalid name`.
- Почему: `display_name` есть у аккаунта всегда, а `real_name` требует скоупа `login:info` и может быть пустым.
- Отклонено: `real_name` с откатом на `display_name`.

### Яндекс: домены эндпоинтов

- Что: авторизация и токен идут на `oauth.yandex.com`, данные пользователя — на `login.yandex.ru/info`.
- Почему: для OAuth домены `.com` и `.ru` равнозначны, выбран `.com`. Для данных пользователя выбора нет: `login.yandex.com/info` отвечает 404, проверено запросом.

### Яндекс: PKCE есть, OIDC нет

- Что: `createUrl` передаёт `code_challenge` и `code_challenge_method=S256`, `getToken` — `code_verifier`. `nonce` не используется.
- Почему: Яндекс ID поддерживает PKCE, но не выдаёт `id_token`, так что привязывать `nonce` не к чему. То же самое у GitHub.
- Не сделано: провайдер-специфичные параметры `force_confirm` и `login_hint`.

## adapters/h11 (`src/adapters/h11/`)

### Заменяемый шаг сохранения вместо колбека `onUser`

- Что: `createStage2Handler` принимает необязательный `saveUser`, который заменяет шаг записи пользователя и аккаунта. По умолчанию — прежний `saveAccountWithUser`, поведение без параметра не меняется. Из `arcwave/h11` теперь экспортируются `saveUser`, `saveAccount`, `saveAccountWithUser` и типы `Account`, `SaveUserStep`.
- Почему:
  - при колбеке приложение получает управление внутри чужой транзакции и должно откуда-то знать, что исключение отменит вход. Это неявное знание, которое живёт только в документации;
  - при заменяемом шаге приложение пишет код шага целиком, и откат виден из обычного чтения кода;
  - исчезает вопрос порядка (до или после создания сессии) и не нужен флаг `created`: внутри своей реализации и так видно, вставили строку или нашли существующую.
- Отклонено: колбек `onUser`.

### Транзакцию открывает сам шаг

- Что: `createStage2Handler` вызывает `saveUser({ account, provider, db })`, где `db` — обычное соединение. Транзакцию открывает приложение внутри своего шага.
- Почему:
  - шаг по умолчанию (`saveAccountWithUser`) открывает транзакцию сам, так что поведение обоих шагов одинаковое;
  - приложение выбирает уровень изоляции, а при нашей транзакции выбора у него нет;
  - исчезает ловушка: когда транзакцию открывали мы, вставка через внешний `db` вместо переданного `tx` вставала во взаимоблокировку до таймаута.
- Цена: атомарность теперь на стороне приложения. Шаг без транзакции при ошибке посередине оставит уже записанные строки, и гарантия «ни пользователя, ни аккаунта» превращается в «как написан шаг». Сессия не создаётся в любом случае, потому что обработчик выходит раньше.
- Отклонено: `db.transaction((tx) => saveUser({ ..., db: tx }))` на нашей стороне.
- Побочные эффекты (письма, аналитика, чужие API) внутрь шага не кладутся: они держат транзакцию открытой. Отдельный хук после коммита — будущая работа.

### Возврат на запрошенную страницу через `?redirect=`

- Что: `createAuthGuard` приписывает к `redirectTo` параметр `?redirect=<путь и query>`, `createStage1Handler` проверяет его и кладёт в куку `arcwave_redirect` (10 минут, httpOnly, как остальные куки потока), `createStage2Handler` уводит на значение куки, а без неё — на свой `redirect`. Кука чистится в `clearAuthCookies`.
- Проверка стоит в stage1, потому что это место, где значение приходит от пользователя. Дальше оно едет в нашей куке.
- Опция `checkRedirect?: RegExp | ((redirect: string) => boolean)` у `createStage1Handler`. Регулярка применяется через `test()`. Правило по умолчанию `checkRedirectLocal` экспортируется из `arcwave/h11`.
- Почему правило по умолчанию спрашивает парсер URL (`new URL(value, PROBE_ORIGIN).origin === PROBE_ORIGIN`), а не сверяет строку:
  - цель — не список разрешённых хостов, а ответ на вопрос «есть ли в значении свой хост». База служебная и произвольная, это просто маркер: если после разбора origin съехал, хост был;
  - парсер выбрасывает табуляции и переводы строки до разбора, поэтому `/<tab>/evil.ru` для строковых проверок выглядит путём, а браузер видит `//evil.ru`. Решает парсер, значит и спрашивать надо его.
- Отклонено:
  - регулярка `^\/(?![\/\\])` («слэш, но не два»): дырява на `/<tab>/evil.ru`;
  - регулярка `^\/[a-z]` по умолчанию: дыр нет, но отвергает `/`, `/2fa` и `/Admin`. Осталась как пример своего правила в README;
  - сверка с настоящим origin приложения: его пришлось бы брать из заголовка `Host`, который за прокси подменяется, либо требовать в конфиге.
- `addRedirectParam` оставляет относительный `redirectTo` относительным: собирать абсолютный `Location` из `req.url` значит зашить в него `Host`.

### Хук `afterLogin` для побочных эффектов

- Что: `createStage2Handler` принимает необязательный `afterLogin({ account, provider, savedAccount, created, sessionId, db })`. Вызывается после `createSession`, то есть транзакция шага сохранения закоммичена и сессия уже существует. Ошибка уходит в `onError` и вход не ломает.
- Почему:
  - письма, аналитика и чужие API внутри шага сохранения держат транзакцию открытой и роняют вход, когда внешний сервис недоступен;
  - вызов после сессии даёт хуку `sessionId` и означает, что вход точно состоялся;
  - семантика ошибки обратная шагу сохранения, и это главное различие между ними: шаг отменяет вход, хук — нет.
- Хук ожидается (`await`), чтобы ошибки были видны и поведение было предсказуемым. Долгие дела приложение кладёт в очередь. Отклонено: запуск без ожидания — в serverless процесс может замереть до отправки.
- Имя: `afterLogin` — совпадает с событием, по которому хук срабатывает, и сразу отличает его от шага сохранения, который вход может отменить. Отклонены:
  - `afterSave`: сохранение заканчивается раньше вызова, между ними проходит `createSession`;
  - `afterSetup`: «setup» в библиотеке читается как настройка при сборке приложения, а хук работает на каждом входе;
  - `onLogin`, `afterCommit`.

### Флаг `created` для признака первого входа

- Что: шаг сохранения возвращает `{ account, created }` (тип `SavedAccount`), `saveUser` — `{ userId, created }`. `created` означает, что строка пользователя вставлена этим входом, то есть это первый вход человека вообще, с любым провайдером.
- Почему: без признака хук не может отличить первый вход от повторного, а это нужно для письма «добро пожаловать».
- Как определяется: `returning({ created: sql`xmax = 0` })`. В Postgres `xmax` равен нулю только у строки, вставленной текущей командой, поэтому upsert, который обновил существующую строку, даёт `false`. Проверено на PGlite.
- Отклонено:
  - не поддерживать признак, пусть приложение пишет его в своей таблице;
  - сравнение `created_at` и `updated_at` на стороне приложения: это догадка по данным, а не факт.
