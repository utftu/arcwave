# Решения

## db (`src/db/schema.ts`)

### Только Postgres (`drizzle-orm/pg-core`)

- Что: схема и запросы пишутся только под Postgres.
- Почему: в Drizzle нет общих для всех диалектов типов колонок и `Db`. `onConflictDoUpdate` и `returning` есть не везде: в MySQL их нет.
- Отклонено:
  - интерфейс `Storage` в ядре и отдельные реализации под каждую базу;
  - фабрики схемы под каждый диалект с объединением типов `Db`.

### Схема по умолчанию — `arcwave`, таблицы `users` / `accounts` / `sessions`

- Что: таблицы создаются в Postgres-схеме `arcwave`, без префикса в именах. `schema: "public"` создаёт их через `pgTable`, без явной схемы.
- Почему: таблицы библиотеки не смешиваются с таблицами приложения, поэтому префикс не нужен. `pgSchema("public")` в Drizzle бросает ошибку.
- Отклонено:
  - `public` по умолчанию;
  - префикс `arcwave_` (`arcwave.arcwave_users`);
  - другие имена по умолчанию для `public`: это скрытая логика. Вместо этого README советует передать `tableName`.

### Точка входа `arcwave/schema` с готовыми таблицами

- Что: `src/db/schema.ts` публикуется как `arcwave/schema`. Помимо функций `create*Table`, он экспортирует готовые `arcwaveSchema`, `users`, `accounts` и `sessions`. Пользователь реэкспортирует их одной строкой из своего файла схемы:

  ```ts
  export { arcwaveSchema, users, accounts, sessions } from "arcwave/schema";
  ```

- Функции `create*Table` остаются и в `arcwave/h11`, для совместимости.
- Для своего имени схемы пользователь сам экспортирует `pgSchema("<имя>")` и вызывает `create*Table({ schema })`.
- Почему:
  - `drizzle-kit` загружает файл схемы через `require()` и берёт только экспортированные `PgTable` и `PgSchema`, имя экспорта не важно;
  - `CREATE SCHEMA` генерируется только для экспортированного `PgSchema`;
  - готовый экспорт избавляет пользователя от ручного `pgSchema("arcwave")` и трёх вызовов `create*Table`.
- Проверено на собранном пакете (`bun pm pack`) в Node 24: `generate` создаёт схему, таблицы, внешние ключи и индексы, `push` применяет изменения.
- Отклонено:
  - только ручной `pgSchema(...)` в файле пользователя без готовых таблиц;
  - `CREATE SCHEMA IF NOT EXISTS` при запуске приложения: миграции идут раньше запуска, и библиотеке понадобились бы права на изменение структуры базы;
  - передача объекта `PgSchema` в опции вместо строки: это меняет API;
  - экспорт из основной точки входа `arcwave`:
    - общие имена `users`, `accounts`, `sessions` попадают в корень пакета;
    - `drizzle-kit` при чтении схемы тянет весь пакет, вместе с провайдерами и `jose`.

### `schemaFilter` — на стороне пользователя

- Что: README просит добавить `schemaFilter: ["public", "arcwave"]` в `drizzle.config.ts`.
- Почему:
  - `push` и `pull` по умолчанию смотрят только схему `public` и молча пропускают таблицы arcwave;
  - для `generate` и `migrate` эта настройка не нужна;
  - конфиг принадлежит пользователю, библиотека не может задать его сама.

### Время — `timestamp with time zone`

- Что: все колонки времени объявлены как `timestamp(..., { withTimezone: true })`.
- Почему:
  - `timestamp` без пояса понимают по-разному: Drizzle пишет и читает `Date` как UTC, а `DEFAULT now()` Postgres пишет в поясе сессии базы;
  - если сессия базы не в UTC, `created_at` и `updated_at` сдвигаются, а сравнения с `now()` в SQL ломаются. Проверено на PGlite с `Europe/Moscow`: сдвиг +3 часа;
  - `timestamptz` занимает те же 8 байт, а Drizzle возвращает тот же `Date`.
- Отклонено: `timestamp` без часового пояса.

## providers (`src/providers/`)

### Яндекс: почта из `default_email`

- Что: `YandexAuth.getUser` берёт `default_email` и считает его подтверждённым. Если поля нет — ошибка `Invalid email`.
- Почему: у Яндекс ID нет аналога `email_verified`. `default_email` — это почтовый ящик самого аккаунта, и по документации массив `emails` сейчас не содержит ничего другого. Допущение записано комментарием в коде, как у GitHub.
- Отклонено: не выпускать провайдер, пока проверить нельзя.

### Яндекс: имя из `display_name`

- Что: `Account.name` — это `display_name`, без него ошибка `Invalid name`.
- Почему: `display_name` есть у аккаунта всегда, а `real_name` требует скоупа `login:info` и может быть пустым.
- Отклонено: `real_name` с откатом на `display_name`.

### Яндекс: домены эндпоинтов

- Что: авторизация и токен идут на `oauth.yandex.com`, данные пользователя — на `login.yandex.ru/info`.
- Почему: для OAuth домены `.com` и `.ru` равнозначны, выбран `.com`. Для данных пользователя выбора нет: `login.yandex.com/info` отвечает 404, проверено запросом.

### Яндекс: PKCE есть, OIDC нет

- Что: `createUrl` передаёт `code_challenge` и `code_challenge_method=S256`, `getToken` — `code_verifier`. `nonce` не используется.
- Почему: Яндекс ID поддерживает PKCE, но не выдаёт `id_token`, так что привязывать `nonce` не к чему. То же самое у GitHub.
- Не сделано: провайдер-специфичные параметры `force_confirm` и `login_hint`.
